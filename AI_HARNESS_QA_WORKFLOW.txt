AI 코딩 에이전트 하네스 & QA 워크플로우 가이드
===============================================

AI 코딩 에이전트(Claude Code, Codex, Copilot 등)를 실제 프로젝트에 투입할 때
"규칙 파일 + 실패 로그 + CI 게이트 + 리뷰"를 어떻게 설계하면 되는지 정리한 문서.
2026년 현업 사례(OpenAI, Anthropic, Google, HumanLayer, Ghostty 등)를 바탕으로 작성.


[0] 용어
--------
- 하네스(Harness): 모델을 감싸서 에이전트로 만드는 실행 루프.
  툴 호출, 파일/쉘 실행, 에러 되먹임, 완료 판단, 승인 흐름을 담당.
  공식: Model + Harness = Agent
- 규칙 파일: CLAUDE.md / AGENTS.md. 에이전트 세션 시작 시 자동 주입되는 지침.
- 훅(Hook): 특정 시점(커밋 전, 작업 완료 전 등)에 자동 실행되는 스크립트.
- 실패 로그: 에이전트가 낸 사고를 기록하는 파일. 규칙의 원천.

- 하네스만 바꿔도 성능 차이가 큼
  (OpenAI 보고: GPT-5.6 Sol ARC-AGI-3 13.3% -> 38.3%, 토큰 1/6)
- 2026년 오픈소스 하네스: OpenAI Codex Harness(Apache-2.0), DeepSeek Harness(MIT)


[1] 최소 하네스 5요소
---------------------
현업에서 정의하는 "최소한 이건 있어야 한다"는 구성.

1. 저장소 가이드 (CLAUDE.md / AGENTS.md)
2. 실행 가능한 로컬 검사 (훅, precommit)
3. 강한 아키텍처 규칙 하나 ("절대 /legacy 건드리지 말 것" 수준)
4. 검증 루프 하나 (테스트/CI)
5. 사람 승인 없이 변경 가능한 범위의 경계

대부분의 팀은 1, 3, 4, 5는 갖추고 2(훅)를 비워 둠.


[2] 규칙 파일 설계
------------------
원칙: 짧게, 목차로, 사건 기반으로.

- 메인 파일은 50~60줄 이내
  - 길어지면 에이전트가 앞부분만 따르고 뒤는 무시함
  - 에이전트 시스템 프롬프트 자체에 이미 ~50개 지시가 있음
  - 연구 결과: 긴 컨텍스트 파일은 성공률을 올리지 않고 비용만 20%+ 증가

- 메인 파일은 포인터(목차) 역할만
  - 상세 지침은 docs/ 하위로 분리
  - 예) "결제 로직 작업 시 docs/payment.md 먼저 읽을 것"
  - 서브디렉토리별 CLAUDE.md, .claude/rules/, skills로 분산

- 넣지 말 것
  - 코드베이스 개요, 디렉토리 트리 (에이전트가 알아서 파악함)
  - 한 번도 문제 된 적 없는 일반론

- 넣을 것
  - 실행 명령어 (test, lint, build, typecheck)
  - 패키지 매니저, 테스트 프레임워크, 포매터
  - 실제 사고에서 나온 금지/강제 규칙
  - "모든 줄은 구체적 실패 사건으로 추적 가능해야 한다"

- 유지보수
  - 주기적으로 오래된 규칙 삭제
  - 백그라운드 에이전트가 stale 문서를 스캔해 정리 PR을 여는 방식도 있음


[3] 실패 로그 -> 규칙 -> 스크립트 승격 절차
--------------------------------------------
로그는 쌓는 게 목적이 아니라 규칙과 스크립트로 바꾸는 게 목적.

(1) 로그 기록 항목
  - 작업 요청 원문
  - 에이전트가 본 컨텍스트 (어떤 파일/지침을 읽었는지)
  - 실행한 명령
  - 에러 원문
  - 사람이 판단한 실제 원인
  - 상태: 미반영 / 규칙화됨 / 스크립트화됨

(2) 규칙으로 변환
  - X: "X 에러 났었음"
  - O: "Y 상황에서는 먼저 Z를 확인할 것"  (원인 + 행동)

(3) 스크립트로 승격 (핵심)
  - 글로 쓴 규칙은 에이전트가 지킬 수도, 안 지킬 수도 있음
    (벤치마크: 악성 요청 66.5%가 텍스트 가드레일 통과)
  - 자동 검사 가능한 규칙은 글 한 줄 + 스크립트 한 줄로 이중화
  - 예시
    규칙: "테스트를 skip/주석 처리하지 말 것"
    스크립트: precommit에서 diff 내 .skip( / xit( / @Ignore grep -> 있으면 커밋 실패
    규칙: "의존성 추가 시 docs/deps.md 갱신"
    스크립트: package.json 변경 && docs/deps.md 미변경 -> CI 실패
  - Claude Code: hooks 설정 (PreToolUse, Stop 등)
  - Codex: sandbox / approval 정책

(4) 정리
  - 규칙/스크립트로 승격된 로그는 아카이브. 에이전트가 매번 읽게 두지 않음

실패 유형별 대응 (Addy Osmani)
  - 관례를 몰랐다          -> 규칙 파일에 추가
  - 파괴적 명령을 실행했다  -> 차단 훅 추가
  - 긴 작업에서 길을 잃었다 -> 플래너 / 실행자로 분리
  - 깨진 코드를 "완료"했다  -> 타입체크/테스트를 완료 조건에 연결


[4] 완료 판정 (Definition of Done)
----------------------------------
"완료"는 증명되기 전까지 주장일 뿐.

- 완료 선언 전 실행할 명령을 고정
  예) typecheck && lint && test && build
- 결과 출력을 그대로 붙이게 함 (요약 보고만 믿지 않음)
- 2단 구조
  - 로컬 Stop 훅: 빠른 검사 (typecheck, lint, 단위 테스트)
  - CI: 느린 검사 (통합 테스트, 보안 스캔, 번들 크기)
- 시각 작업은 스크린샷 제출
- LLM 기능은 eval 세트로 검증
- "왜 완료라고 착각했는지"도 실패 로그에 기록 -> 다음 검증 규칙


[5] 리뷰 설계
-------------
(1) 리뷰 트리거: "신규 여부"가 아니라 "영향 범위"
  - 기존 코드 수정이 신규보다 위험한 경우가 많음 (사이드이펙트)
  - 자동 리뷰 대상 경로
    - 공통 모듈 / 유틸
    - 인증, 권한
    - 결제
    - DB 스키마, 마이그레이션
    - 설정 파일 (env, CI/CD, 배포)
    - 의존성 추가/변경

(2) 사람 승인 필수
  - 합의된 스코프 밖 쓰기
  - 파괴적 명령 (rm -rf, force push, DROP, 데이터 삭제)
  - 프로덕션 배포
  - 보안 경계 변경

(3) 서브에이전트 리뷰어
  - 원칙: 작성 과정을 못 본 별도 세션이 검토
    (Anthropic 연구: 자기 채점은 일관되게 긍정 편향)
  - 체크리스트
    - 요청 원문 vs diff: 시킨 걸 했는가, 안 시킨 걸 건드렸는가
    - 완료 조건 재실행: 테스트를 직접 돌려 확인
    - 금지 규칙 위반 여부
    - 과거 실패 패턴 재발 여부
  - 출력: 통과/반려 + 사유만
  - 반려 -> 재작업 -> 재리뷰 루프에 횟수 제한 (무한루프 방지)
  - 비용이 2배 가까우므로 영향 범위 큰 작업에만 적용

(4) 자율성 다이얼
  - 공격적: 의존성 범프, 문서 동기화, 소규모 리팩토링
  - 보수적: 인증, 결제, 데이터 마이그레이션, 인프라


[6] PR(diff) 크기 상한
----------------------
- 한 PR 상한 설정 (예: 300줄). 초과 시 쪼개서 오거나 명시적 승인
- 목적: 리뷰 품질 유지. 큰 변경을 막는 게 아니라 작은 PR 여러 개로 나누게 함
- 2,000줄 diff는 사람이 못 봄 -> 대충 보고 머지 -> 사고
- 테스트/하네스가 충분히 강해지면 자연스럽게 필요 없어지는 과도기 장치

측정 지표
  - 생성 코드 줄 수 (X)
  - 사이클 타임, 리뷰 부하, PR 큐 깊이, 첫 리뷰까지 시간 (O)


[7] 테스트 오염 감시
--------------------
- 에이전트는 CI 통과가 목표가 되면 테스트를 느슨하게 고치거나 skip함
- 테스트 파일 변경은 별도 리뷰/승인 대상
- 기존 테스트 수정/삭제 시 사유를 PR에 명시
- 커버리지 하락 시 CI 실패
- 테스트 생성을 리뷰어 측에 맡기거나, 리뷰어가 테스트 엄격성도 검토
- TDD 강제: 코드 작성 전 테스트부터 (완료 조건을 코드로 고정)


[8] 배포 후 구간
----------------
- 프로덕션 에러/알림 -> 실패 로그 -> 규칙화 경로 연결
- 롤백 절차 문서화 (에이전트도 실행 가능하게)
- 카나리 / 스테이징에서 묵힌 뒤 본배포


[9] 보안 / 샌드박스
-------------------
- CI: 의존성 취약점 스캔, 시크릿 스캔, 타입체크 (환각된 API 시그니처 자동 검출)
- 신규 패키지 추가는 리뷰 필수
- 샌드박스
  - 쓰기 가능 디렉토리 제한
  - 네트워크 허용목록 (pastebin 등 외부 sink 차단)
  - 시크릿 격리, 단기 토큰, 로그 마스킹
  - 읽기/쓰기 툴 분리, 파괴적 작업은 명시적 승격
- 에이전트 내장 브라우저 취약점 사례 (2026.10): 내장 브라우저에 일반 브라우저 이상의 권한을 주지 말 것


[10] 결정 로그 (ADR)
--------------------
- 대화 중 내린 설계 결정("이건 이렇게 가자")은 짧게 ADR로 기록
- 실패 로그와 별개
- 안 남기면 다음 세션에서 같은 논의 반복


[11] 관측
---------
- 명령 / 결과 / 빌드 / 테스트 로그를 통합 기록
- 에이전트가 자기 동작을 보고 복구할 수 있게 (Simon Willison 방식)
- 세션 로그는 append-only로 (DeepSeek Harness가 핵심 기능으로 내세움)


[12] 도입 순서 (권장)
---------------------
1. 규칙 파일 60줄 이내로 작성, 상세는 docs/로 분리
2. 완료 판정 명령 고정 + Stop 훅
3. 실패 로그 양식 + 상태 컬럼
4. 규칙 중 자동 검사 가능한 것부터 precommit/hook으로
5. 리뷰 트리거 경로 목록 (인증/결제/설정/의존성)
6. PR 줄 수 상한
7. 테스트 파일 변경 감시
8. 배포 후 피드백 경로
9. 서브에이전트 리뷰어 (영향 범위 큰 작업만)
10. 분기별 규칙/워크플로우 점검, 효과 없는 것 삭제

소규모 팀 자율성 확대 순서
  1) 테스트 추가, 소규모 버그 수정
  2) 저위험 리팩토링
  3) 의존성 업데이트, 문서 동기화
  4) 그 다음에야 모듈 간 기능 작업
